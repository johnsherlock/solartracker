# P-012: Design beta access request and invite flow

## Objective

Define how prospective users request beta access, how admins approve them, and
how the invitation is communicated.

## Decision

The beta access request flow is the existing Google sign-in path. No separate
pre-sign-in request form is needed.

- Prospective users sign in with Google at `/sign-in`
- Sign-in page copy makes clear that signing in is how you request beta access
- On first sign-in, a user record is created with status `awaiting_approval`
- The `/waiting` page explains that access is pending admin approval
- Admin approves the user in the admin area; an approval email is sent
- User signs back in and enters the app

The `/sign-in` copy update is a minor change the operator will make directly.
No invite tokens, dedicated request form, or additional infrastructure is
required.

## Out of Scope

- Pre-sign-in beta access request form (not needed; U-014 is superseded)
- Invite-token or secret-URL flows (explicitly deferred in Decision 0006)
- Decline notification email (deferred)

## Dependencies

- `P-001`, `P-007`, `P-013` (all done)
- Decision record `0006-beta-auth-approval-and-provider-gating.md`

## Acceptance Criteria

- The beta request, approval, and invitation flow is documented end to end ✅
- The flow is: sign in with Google → `/waiting` → admin approves → email → re-sign-in
