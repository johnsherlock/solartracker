# P-077: Split admin identity from end-user accounts and add dedicated admin login

## Objective

Separate operator identities from normal product users so admins no longer
behave like end users in the data model or auth flow.

Today the product models admins as rows in `users` with `role = admin`. That
creates the wrong shape for the business domain:

- admins can look like they should have installations, provider connections,
  and personal app context
- `approved_by` points to `users.id`, which ties approval provenance to the
  end-user table instead of to an operator identity
- auth and routing must keep working around the idea that an admin is "just
  another user with a special role"

This story should introduce a distinct `admin_users` identity, give admins a
dedicated login area, and remove admin-role concerns from the normal `users`
table.

## Scope

### Data model split

- Create a dedicated `admin_users` table/entity for operator accounts
- Remove the `role` concept from the normal `users` table
- Refactor approval provenance so `users.approved_by` references
  `admin_users.id` instead of `users.id`
- Update schema, migrations, seeds, and server-side types so admin identity is
  modeled separately from end-user identity throughout the rewrite

### Admin bootstrap

- Bootstrap one initial admin account for local/dev and first beta operations
- The bootstrap path can be seed-based or migration-assisted, but it must be
  explicit and repeatable
- The initial admin account should not require a corresponding end-user row,
  installation, provider connection, or signed-in app context

### Dedicated admin auth

- Add a dedicated admin login area separate from the normal end-user sign-in
  flow
- For the first pass, admin auth can use a username/password flow rather than
  Google/email login
- Admin auth state should resolve to the new `admin_users` identity, not to a
  normal `users` session with elevated role flags
- Successful admin login should land in the admin area, not in user-facing app
  routes

### Admin area entry point

- Add or firm up an `/admin` login and post-login handoff flow
- After admin login, route the operator into the admin area, which currently
  contains the user-management screen
- User-facing signed-in routes should remain accessible to admins only through
  explicit impersonation, not by virtue of being admins

### Refactor follow-through

- Update approval, impersonation, and routing code paths to use the separate
  admin identity where appropriate
- Remove assumptions that admin session data can be resolved from the normal
  `users` table
- Update documentation and tests that currently describe or assert
  `user.role = admin`

## Out of Scope

- Multi-admin invitation or self-serve admin-account management
- SSO or Google-based admin auth in this first pass
- Rich admin dashboard modules beyond the existing user-management entry point
- Fine-grained permission tiers inside `admin_users`
- Reworking the broader beta approval product flow beyond what is needed for
  the identity split

## Acceptance Criteria

- The rewrite has a dedicated `admin_users` identity/table separate from
  `users`
- Normal end-user rows no longer carry an admin `role` field
- `users.approved_by` references `admin_users.id`
- A bootstrapped admin account can sign in through a dedicated admin login area
  using username/password
- Successful admin login lands on the admin area rather than a normal
  user-facing route
- The bootstrapped admin account has no installation, provider connection, or
  end-user app context of its own
- Existing admin approval flows still record approval provenance correctly
  after the refactor
- Existing impersonation flows can still enter user-facing screens from the
  admin area using the separate admin identity model
- Tests or verification coverage exist for the schema change, admin login, and
  approval provenance path

## Dependencies

- `P-040` for the existing admin approval workflow
- Existing auth/session infrastructure in `apps/web`
- Existing impersonation workflow (`P-045`) and follow-on routing/banner work
  in `P-076`

## Notes

- This is intentionally a deeper architectural story than `P-076`. `P-076`
  should assume the admin/operator concept is real and visible in the product;
  this story makes that identity boundary true in the persistence and auth
  model.
- It is acceptable for the first admin auth pass to use a deliberately simple
  bootstrap credential flow as long as it is isolated to the admin area and
  does not leak back into the normal user model.
- After this lands, admin behavior should read as:
  - operator logs into `/admin`
  - operator manages users from the admin area
  - operator enters user-facing screens only by impersonating a chosen user
