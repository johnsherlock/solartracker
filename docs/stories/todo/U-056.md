# U-056: Define missing-day estimation model and trust language

## Objective

Define how the product should estimate missing historical days for `Range
History`, how confidence should vary by gap type, and how estimated values
should be described so the app remains useful without pretending the estimates
are measurements.

## Scope

- Define the first-pass estimation hierarchy for missing days, including
  candidate inputs such as:
  - neighbouring measured days
  - same-season / same-date analogs from previous years
  - optional external generation/weather context for generation estimates
- Record the preferred first external estimation source, if one is used, and
  what role it plays in the estimation hierarchy
- Define how the model should vary by gap size, for example:
  - short gaps
  - medium gaps
  - long gaps
- Define which outputs are in scope for first-pass estimation:
  - generation
  - export
  - import
  - immersion
  - day-level financial derivatives
- Define what remains out of scope for the first pass
- Define how estimated days and estimate-influenced totals should be labeled in
  Range History
- Define whether and how confidence bands or confidence labels should appear

## Out of Scope

- Implementing the estimation logic
- Adding any UI controls or backend jobs
- Changing the Historical Day screen

## Acceptance Criteria

- The intended first-pass estimation inputs and heuristics are documented
- The model clearly distinguishes between short-gap and longer-gap behavior
- The document states which day-level metrics are estimated directly and which
  are derived secondarily
- If external estimation inputs are retained, the doc identifies PVGIS as the
  preferred first source for missing-day generation estimates and makes clear
  how Open-Meteo historical weather can complement or backstop it
- The doc makes clear that external weather/PV context primarily supports
  generation estimation rather than full household-behavior reconstruction
- The trust/disclosure language for estimated days and estimated totals is
  clear enough to implement without reopening the product intent
- The doc explicitly states that Historical Day remains measured-data-only for
  missing dates
