# P-058: Make Range History load incrementally

> Deferred: no longer planned after the priced daily rollup work restored
> acceptable bounded-range `/range` performance. Keep this doc only as a
> historical fallback idea if future real-world profiling shows a new blocking
> frontend bottleneck.

## Objective

Improve perceived performance on `/range` by letting the screen start painting
 before all secondary data is ready, rather than blocking the entire route on
 all-time finance and payoff computations.

## Scope

- Split the Range History load path into:
  - fast core range content
  - slower secondary finance/payoff content
- Ensure the page can render its shell and first useful content as soon as the
  visible range data is available
- Defer the all-time finance/payoff work so it no longer blocks the first
  useful render
- Keep the user-facing loading states coherent while sections fill in
- Preserve current financial accuracy when the deferred section eventually
  resolves
- Instrument or otherwise make the staged loading behavior easy to verify

## Out of Scope

- Changing the underlying range pricing model
- Introducing the long-term priced daily rollup layer
- Optimizing `All` mode
- Major chart-library or frontend redesign work

## Acceptance Criteria

- `/range` starts painting before all secondary finance/payoff data is ready
- The page shell, period controls, and first useful range summary do not wait
  for all-time recovery/payoff computations
- Deferred sections have clear loading states rather than blank gaps or
  confusing partial content
- When the deferred finance/payoff data resolves, the page updates without a
  full reload
- Current bounded range behavior remains correct for the already-rendered
  visible range summary and charts
- `All` mode behavior is unchanged unless required incidentally by the refactor

## Dependencies

- Existing Range History route and component structure
- `P-054` as the branch/home for current Range History interpretation work
