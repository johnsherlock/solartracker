# P-086: Automate provider-setup-triggered onboarding backfill

## Objective

Turn successful provider setup into a fully automated onboarding path by
triggering historical backfill in the background, persisting progress/failure
state, and giving both users and operators enough visibility to understand what
is happening without manual intervention.

## Scope

- Trigger initial historical backfill automatically after a provider connection
  is validated successfully
- Use the agreed Vercel-native background execution model rather than manual
  scripts as the primary runtime path
- Persist enough state to represent at least:
  - pending
  - running
  - completed
  - failed / needs attention
- Prevent duplicate onboarding backfills for the same installation
- Define the user-facing behavior while onboarding backfill is still running,
  including:
  - whether the user can enter the app immediately
  - what “history still preparing” messaging appears
  - what the next useful action is
- Define operator-visible status/logging expectations so support can tell
  whether onboarding backfill started, is still running, completed, or failed
- Leave a clear integration point for later completion notification delivery
  such as `P-067`

## Out of Scope

- Rich historical outage/trust analytics beyond what onboarding needs
- Full notification implementation beyond the handoff point to `P-067`
- Tariff-edit-triggered rebuild behavior
- Estimated missing-day reconstruction for range history

## Acceptance Criteria

- A valid provider connection automatically triggers initial historical
  backfill for that installation
- Background execution uses the agreed Vercel-native runtime pattern
- Progress and failure state are persisted in a supportable way
- Duplicate onboarding backfills are avoided for the same installation
- Users see a coherent onboarding/backfill state instead of being left to infer
  whether history is ready
- Operators can inspect enough status to support a user without resorting to
  guesswork
- Completion state is explicit enough for later notification delivery and for
  the app to know when history is ready

## Dependencies

- `FE-019`
- `FE-012`
- `P-006`
- Successful provider connection persistence in `P-038`
- Existing provider day-detail / ingestion foundations

## Notes

- This is the missing end-to-end launch-critical slice in the current backlog.
- The beta does not need perfect historical trust modeling here, but it does
  need a real automated path from “provider connected” to “useful history is
  loading or ready”.
- Favor idempotent, chunked, inspectable execution over a thin fire-and-forget
  path that is hard to support when a user gets stuck.
