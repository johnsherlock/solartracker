# P-071: Build self-serve account deletion and data removal flow

## Objective

Implement the signed-in Settings flow that lets a user delete their account and
all associated product data, so the privacy promise shown on the sign-in page is
true in the shipped product rather than only implied by architecture notes.

## Scope

- Add a user-facing account deletion flow in Settings
- Require an intentional confirmation step before destructive deletion proceeds
- Delete or schedule deletion of the user's owned product data in line with the
  privacy and retention model already defined in architecture/docs
- Sign the user out cleanly once deletion completes
- Surface clear success/failure treatment so the user understands whether the
  deletion finished or needs support follow-up
- Ensure the flow behaves safely for beta operators, including any necessary
  constraints around admin accounts or active impersonation sessions
- Add automated coverage for the main deletion-path and access-removal behavior

## Out of Scope

- Admin/operator bulk deletion tooling
- Data export / portability flows
- Complex retention exemptions beyond the already-defined privacy model
- Broader profile-management redesign outside the deletion entry point required
  for this feature

## Acceptance Criteria

- Signed-in users can initiate account deletion from Settings
- Deletion requires an explicit confirmation step and is not easy to trigger by
  accident
- After deletion, the user no longer has access to their account or app data
- The implementation follows the documented ownership/deletion model rather than
  leaving orphaned user-owned records behind
- Tests cover the main deletion flow and confirm the user cannot continue using
  the deleted account normally afterward

## Dependencies

- `FE-007`
- `P-007`
- `Q-005`
- Existing signed-in Settings shell

## Notes

- The UX entry point should match the promise already visible on the sign-in
  page: "You can delete your account and all data at any time from Settings."
- If the deletion workflow ends up being asynchronous for operational reasons,
  the user-facing messaging must still make the result and access loss explicit.
