# P-083: Migrate the rewrite to `johnsherlock/solartracker` on `main`

## Objective

Complete the repository cutover from `pv-manager`'s temporary `v2` rewrite line
into `johnsherlock/solartracker` so the rewrite becomes the canonical app on
`main`, the obsolete Replit-era app is removed entirely, and the surviving git
history preserves the meaningful rewrite-era evolution of the product.

## Scope

- Define the cutover sequence for replacing the current contents of
  `johnsherlock/solartracker` with the rewrite from this repository
- Preserve git history from the rewrite onward using a filtered migration rather
  than a fresh copy where practical
- Use judgment to keep the history that matters to the rewrite and exclude
  clearly obsolete baggage such as the legacy `V1/` app and unrelated old repo
  artifacts
- Establish `main` in `johnsherlock/solartracker` as the canonical shipping and
  default branch for the rewrite
- Remove the obsolete Replit-era app from `johnsherlock/solartracker`
- Update CI, PR, deployment, and documentation assumptions so they target
  `main` rather than `v2`
- Find and update repo-local workflow instructions and skills that still assume
  `v2`, including story-completion and story-implementation helpers
- Define the cleanup and archival posture for the old `pv-manager` repository
  and the temporary `v2` branch once the migration is complete and verified

## Out of Scope

- Preserving the old contents of `johnsherlock/solartracker` on `main`
- Keeping the Replit-era app around as an in-repo fallback
- Preserving every historical path from `pv-manager` regardless of relevance
- Broad codebase refactors unrelated to the repository migration

## Acceptance Criteria

- `johnsherlock/solartracker` `main` contains the rewrite as the canonical app
- The obsolete Replit-era app in `johnsherlock/solartracker` is fully removed
- The migrated history preserves the meaningful rewrite-era evolution of the
  app, docs, and supporting repo assets rather than starting from a single
  import commit
- The migration approach explicitly documents which paths/history were kept and
  which were intentionally excluded
- CI, PR, deployment, and release assumptions point at `main` rather than `v2`
- Repo docs and skills no longer describe `v2` as the active rewrite branch
- Identified skill/workflow references such as `complete-story` and
  `plan-and-implement-story` are updated or tracked as part of the cutover
- The cutover and cleanup sequence is documented clearly enough to execute
  without guesswork

- Existing rewrite deployment path being ready for the canonical `main` branch

  rename.

  one canonical app.

  the rewrite's real development history while shedding obvious dead weight.
