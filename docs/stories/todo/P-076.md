# P-076: Fix admin routing and add impersonation banner

## Objective

Ensure admin users are routed correctly and that the impersonation context is
clearly visible when an admin is browsing the app as another user.

Currently the middleware grants admins a blanket bypass of all routing rules,
which means an admin who signs in without impersonating anyone can reach `/live`
and see their own installation data (or no data if they have none). Admins are
operator accounts and should not have a personal app context — they should land
in the admin panel and enter user-facing screens only by impersonating a
specific user.

Once impersonating, there is no visible indicator that the data shown belongs
to another user, and there is no way to stop the impersonation without
navigating back to `/admin/users` directly.

## Scope

### Middleware routing fix

- When an admin is authenticated but has no active impersonation cookie,
  redirect any access to user-facing routes to `/admin/users`
- When an admin has an active `impersonating_user_id` cookie, allow through to
  all normal user-facing routes (they are viewing the app as that user)
- Admin routes (`/admin/*`) are always accessible to admins regardless of
  impersonation state

### Impersonation banner

- Add an impersonation banner to all signed-in screens
- The banner shows the email address of the user being impersonated and a
  "Stop impersonating" button
- Clicking Stop clears the impersonation cookies and redirects to `/admin/users`
- The banner is only visible when the active session is an admin with an
  impersonation cookie set; normal users never see it

### Screens to update

The banner must appear on:
- Live screen
- Historical Day screen
- Range History screen
- Calendar screen
- Leaderboard screen
- Settings layout

## Implementation Notes

- `SignedInHeader` is a client component; the impersonation email should be
  read server-side (via `cookies()` from `next/headers`) and passed in as a
  prop from each page/layout server component
- The `stopImpersonation` server action already exists in
  `app/admin/users/actions.ts` and can be imported directly
- The banner should be visually distinct (e.g. amber/warning tone) so the
  operator always knows they are in a delegated context
- The seed admin user has no installation and no provider connection — this is
  correct and deliberate; the routing fix makes that explicit in the product

## Acceptance Criteria

- An admin who signs in and navigates to `/live` without impersonating anyone
  is redirected to `/admin/users`
- An admin who clicks "View as user" is redirected to `/live` and sees that
  user's data with an impersonation banner visible
- The banner shows the impersonated user's email and a working "Stop
  impersonating" button
- Clicking Stop returns the admin to `/admin/users` with no impersonation cookie
- Normal users never see the banner
- All six signed-in surfaces (Live, Historical Day, Range History, Calendar,
  Leaderboard, Settings) show the banner correctly when impersonating

## Dependencies

- Existing impersonation infrastructure: `startImpersonation` / `stopImpersonation`
  actions and `resolveEffectiveUserId` in `auth-helpers.ts`
