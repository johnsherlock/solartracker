# FE-018: Notifications and Email Engagement

## Goal

Turn the product's first notification ideas into a coherent feature that owns
user-facing delivery, starting with email and in-app preference-driven triggers.

This feature should cover both trust/operational notifications and engagement
notifications, so users hear from the product when action is needed or when new
insight is worth returning for.

## Status

`Todo`

## Feature Completion Criteria

- The product has one clear home for notification delivery behavior rather than
  scattering it across Data Health, Settings, and later engagement ideas
- Users can manage the relevant notification preferences from the existing
  Settings screen
- Event-driven notification triggers are defined for onboarding, outages,
  tariff validity, and standout-performance events
- Notification delivery is deduplicated, preference-aware, and auditable enough
  for beta support
- The first recurring summary digests are scoped as part of the same feature so
  periodic engagement does not become an orphaned later idea

## Included Stories

Stories in intended execution order:

1. [`P-027`](../backlog.md) Deliver outage and anomaly notifications
2. [`P-067`](../backlog.md) Send historical backfill completion notifications
3. [`P-068`](../backlog.md) Deliver configurable best-day notifications
4. [`P-070`](../backlog.md) Deliver tariff end-date reminder emails
5. [`U-016`](../backlog.md) Design periodic summary digests
6. [`P-069`](../backlog.md) Build monthly and yearly performance roundup notifications

## Dependencies

- `FE-014` for the existing `/settings/notifications` preference home
- `FE-012` for deployed job, queue, workflow, and email-delivery architecture
- `FE-002` for persisted outage/anomaly and coverage signals that feed trust
  notifications
- `FE-015` for high-quality financial language that digest and achievement
  emails should reuse rather than inventing a second value narrative

## Deferred From This Feature

- Push notifications if email plus in-app state is sufficient at first
- AI-generated personalized narratives
- Multi-tenant/provider-branded notification programs
- Fine-grained per-channel routing rules beyond the first simple preference set

## Notes

- `FE-014` already created the Settings home and first saved preferences for
  notifications. This feature is about making those preferences do real work.
- Delivery should be event-driven and preference-aware, but the actual sending
  layer may still use a dedicated email provider rather than Vercel-native mail
  infrastructure.
- Backfill-complete notifications are especially important for beta onboarding:
  users need a clear signal that their history is ready to explore.
