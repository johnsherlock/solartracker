# FE-016: Estimated Backfill For Missing Range History Days

## Goal

Give `Range History` a clearly-signalled way to include estimated values for
missing historical days so longer outages do not leave large blind spots in
period-level charts and totals.

This feature is intentionally narrower than a general provider-recovery or data
health feature:

- it applies to the `Range History` surface only
- it does not change the dedicated Historical Day screen for missing days
- it keeps measured data and estimated data explicitly separate

The product goal is not to pretend we know the exact missing values. It is to
offer a useful, transparent “best estimate” mode that users can toggle on or
off when looking at range-level history.

## Status

`Todo`

## Feature Completion Criteria

- Missing historical days can have persisted estimated daily values separate
  from measured daily values
- Range History can toggle between:
  - measured data only
  - measured data plus estimates for missing days
- Estimated days are visually obvious in charts, tables, and explanatory copy
- Historical Day remains unchanged: a missing day still presents as missing
  rather than pretending to have real day-detail telemetry
- The estimation model distinguishes between short gaps and longer gaps rather
  than using one naive rule for every outage
- The product can explain, in plain language, where the estimate came from and
  how much confidence to place in it
- Downstream period totals that include estimates are clearly labeled as such

- `FE-015` for the broader range-history financial/value model
- `FE-002` for adjacent outage and data-trust concepts, though this feature is
  intentionally narrower and range-specific
- The raw half-hour interval source-of-truth and day-level reporting layers

## Deferred From This Feature

- Reconstructing minute-by-minute or half-hour historical detail for missing
  days
- Changing the dedicated Historical Day screen to show synthetic telemetry
- Claiming exact root cause for why data was missing
- Silent substitution of estimated values into all product surfaces
- AI-generated “best possible” explanations that overstate confidence

## Notes

- The safest first implementation is likely:
  - estimate generation first
  - estimate other day-level values only when the model can explain itself
  - derive financial outputs only from the stored estimated day-level energy
    values and mark them as estimate-based
- Candidate estimation inputs include:
  - neighbouring measured days
  - seasonal analogs from nearby dates in previous years
  - external generation/weather context where it materially improves
    confidence
- If an external source is introduced, the preferred first source for missing
  day generation estimates is PVGIS via the JRC non-interactive API, using the
  installation location and known system characteristics where available.
- Open-Meteo Historical Weather API (`/v1/archive`) remains a useful secondary
  context or fallback input, but should be treated as supporting evidence for
  generation estimation rather than as a full reconstruction source for
  household import, export, or immersion behavior.
- Different strategies may be more appropriate for:
  - short gaps of a few days
  - medium gaps of one to a few weeks
  - long gaps where confidence should drop materially
- Persisted estimates should live alongside an explicit flag and provenance
  metadata, not overwrite measured summaries.
